# Epic E1.5 — §9 Proof Run

## Context

The engine is assembled and merged to `milestone/M1`: E1.1–E1.4 delivered the client,
the parser/coercion crux, the permission-scoped proof tools, and the §5 loop behind the
§2 CLI — 109 offline tests green, end-to-end verified against a scripted stand-in
server. E1.4's acceptance criterion was explicit: the proof needs only a task file, a
tools.json, and the CLI.

This Epic runs the proof the whole project exists to attempt (CONTRACT.md §9): give
`qwen2.5-coder:14b` a 3-step task — **read** a file, **edit** one line, **run** a test
that checks the edit — and confirm the loop converges to a passing result with a clean
transcript, **reproducibly** (Milestone-level decision, 2026-07-09: three consecutive
converging runs), **inside a container** (§10.3).

This is the only Epic in M1 that touches the live model and the GPU. Host facts
(binding): Ollama runs as a Docker container at `http://localhost:11434`; there is no
`ollama` CLI on the host; the GPU (16 GB, shared with ComfyUI) fits one heavy consumer
at a time.

---

## Problem Statement

The project's founding question — can a local model, reached over Ollama's HTTP API,
reliably drive a tool-calling loop to a correct, verifiable result? — is still open.
Every offline test passes, but no model has ever driven this engine. Until the §9 proof
converges reproducibly, the roadmap past M1 is speculative. This Epic either retires
that risk or surfaces exactly where the engine fails against reality.

---

## Goals

By the end of this Epic, the system must have:

1. A committed, self-contained proof fixture: a workspace with a file to edit and a
   test that verifies the edit, a `task.md` with the 3-step instruction, and a
   `tools.json` scoping the three tools to exactly what the proof needs
2. A containerized invocation path: the runner executes inside a container (§10.3)
   against the host's Ollama at `http://localhost:11434` (endpoint overridable), with
   one-command entry (`proof/run-proof.sh`)
3. A mechanical cleanliness check: a small stdlib checker that validates a transcript
   against the milestone's acceptance wording — exit 0 / `status: "completed"`, every
   step with a well-formed `tool_call` and `tool_result`, no unrepaired error in the
   final iteration, and the edit verified by the test the model ran
4. **The proof itself: three consecutive converging runs**, workspace reset between
   runs, transcripts committed as milestone artifacts under `proof/artifacts/`
5. A Delivery Notice recording, per run: `iterations`, `tokens`, `duration_ms`, and
   any repair rounds observed (repairs are allowed anywhere except unrepaired in the
   final iteration — visible repairs are the §5 design working, not a defect)

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Change engine code (`local_agent_runner/`) — engine defects discovered here are
  **reported to the Milestone Chat**, not patched in this Epic (that would bypass a
  review gate; a fix would be a separate authorized change)
- Validate models other than `qwen2.5-coder:14b`, or tune Ollama options beyond what
  convergence needs
- Add tools, permissions features, retry/backoff, or CLI flags
- Prove statistical reliability beyond the milestone's settled definition (three
  consecutive converging runs — do not reopen)

## Scope of Work

### 1. Proof fixture (`proof/`)

**Must include:**
- `proof/workspace-template/` — the pristine workspace copied fresh for each run:
  - a small source file with one clearly identifiable line to change (e.g.
    `app.py` containing `VALUE = 41`)
  - a plain-Python test runnable without pytest (e.g. `test_app.py` that exits 0 iff
    the edit is correct — `python3 test_app.py`; §9 says "run a test", and a
    dependency-free script keeps the container minimal)
- `proof/task.md` — the 3-step instruction, written for a local 14 B coder model:
  read the file, change the one line, run the test, and state the result. Task wording
  is this Epic's to tune (it is the prompt, not the engine)
- `proof/tools.json` — `enabled`: the three proof tools; `allow_paths` scoped to the
  run workspace only; `allow_commands` permitting exactly the test command;
  a `timeout` generous enough for the test (§4 shape, E1.3 semantics)

### 2. Containerized invocation (`proof/Dockerfile`, `proof/run-proof.sh`)

**Must include:**
- A minimal image (e.g. `python:3.12-slim`) with the package installed
  (`pip install .`) — no dev extras needed at proof time
- `run-proof.sh`: builds the image, then for run *n* in 1..3: resets the workspace
  from the template, invokes the containerized CLI
  (`--model qwen2.5-coder:14b --task ... --tools ... --transcript
  proof/artifacts/transcript-run<n>.json`), runs the checker on the transcript, and
  stops at the first failure (consecutive means consecutive)
- Container networking that reaches the host's Ollama (Linux host: `--network host`
  is the settled default; endpoint overridable via `--endpoint` / an env var for
  other setups)
- The script prints a per-run PASS/FAIL line and a final verdict; it must be the one
  command a reviewer runs to reproduce the proof

### 3. Transcript checker (`proof/check_transcript.py`)

**Must include (stdlib only):**
- Validates the §3 shape keys, `status == "completed"`, non-empty `final_answer`
- Every transcript step has a well-formed `tool_call` (`name` a non-empty string,
  `args` an object) and a non-empty string `tool_result`
- No unrepaired error in the final iteration: the last step, if any, is not an error
  result (error = a step whose `tool_result` matches the E1.3 error-message forms /
  the run's repair feedback; the checker's exact detection rule is settled by the
  Coding Agent and recorded in the Delivery Notice)
- The edit is verified **by the workspace state**: the checker (or the script)
  additionally asserts the workspace file contains the edited line and the test
  passes when re-run directly — belt and braces beyond the model's own test step
- Offline unit test for the checker itself (`tests/test_check_transcript.py`) against
  synthetic pass/fail transcripts — the checker is acceptance machinery and must not
  be wrong

### 4. The proof runs

**Must include:**
- GPU coordination first: confirm with the human operator that ComfyUI is idle
  (one heavy consumer at a time) and that `qwen2.5-coder:14b` is pulled and served
  at `http://localhost:11434`
- Three consecutive converging runs via `run-proof.sh`; the three transcripts
  committed under `proof/artifacts/` (these are milestone artifacts — the Milestone's
  completion criteria name them)
- If a run fails to converge: iterate on `task.md` wording / `tools.json` scoping /
  Ollama `options` if warranted — never on engine code — and restart the count of
  three; keep failed transcripts under `proof/artifacts/attempts/` (cheap, honest
  evidence and §6 cost visibility)
- If failure looks like an **engine defect** (parser misses a delivery-mode variant,
  loop misroutes, tool misbehaves): STOP, capture the transcript, and report to the
  Milestone Chat with the evidence

## Technical Constraints

**Model:** `qwen2.5-coder:14b` at `http://localhost:11434` (endpoint overridable)
**Container:** runner always inside a container (§10.3); Linux host networking via
`--network host` (settled); image minimal, package installed from the repo checkout
**Checker/fixture:** Python stdlib only; test in the workspace runnable without pytest
**GPU:** contended with ComfyUI — coordinate with the human operator before runs; one
heavy consumer at a time
**Engine:** read-only — no changes under `local_agent_runner/`

**Internal Dependencies:**

**External Dependencies:**

  pulled
- GPU availability (ComfyUI idle during proof runs)
- Docker available to build/run the proof container

**Blockers:**
- GPU/host availability is operator-scheduled; runs cannot proceed without it

## Execution Notes

- Build and green everything offline first (fixture, container, checker, checker
  tests); go to the GPU only when the whole harness is ready — GPU time is the scarce
  resource.
- Keep the workspace tiny and the editable line unmistakable; the §9 proof is about
  the loop, not about code comprehension difficulty.
- Prompt-tuning is legitimate scope; document final task wording rationale briefly in
  the Delivery Notice if it evolved.
- Expect the content delivery mode (qwen emits fenced JSON, per §1.2) — the recorded
  fixtures show what the wire traffic should look like.
- Record wall-clock and `tokens` per run — these numbers seed §6's cost-visibility
  baseline for everything after M1.

## Notes

- Epic-level decisions settled in this spec (do not reopen without a spec amendment):
  - **Dependency-free test script** (`python3 test_app.py`-style) instead of pytest
    inside the proof container.
  - **`--network host`** as the settled Linux container-networking default; endpoint
    remains overridable.
  - **Workspace reset from a pristine template before every run** — run 2 must not
    find run 1's edit already applied.
  - **Failed attempts are kept** under `proof/artifacts/attempts/` and the count of
    three restarts after any failure ("consecutive" is literal).
  - **Engine is read-only in this Epic** — defects escalate to the Milestone Chat
    with transcript evidence; they are never patched inline.
- Milestone-level decision (2026-07-09, do not reopen): "reproducibly" = three
  consecutive converging runs.
