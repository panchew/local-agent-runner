# Epic E1.1 — Ollama HTTP Client

## Context

CONTRACT.md v0.1 is accepted and Milestone M1 (First-Proof Milestone) exists to prove the
core tool-calling loop end-to-end. Every loop iteration is one `POST /api/chat` round trip
to a local Ollama server, so a correct, typed HTTP client is the foundation everything else
in this Milestone builds on.

The host constraints are measured facts (CONTRACT.md §1), not assumptions: Ollama runs as a
Docker container serving `http://localhost:11434`; the `ollama` binary is **not** on PATH
and must never be shelled out to. The runner itself always runs inside a container
(CONTRACT.md §10.3).

E1.1 is one of three mutually independent Epics (E1.1–E1.3). It is sequenced first because
it also bootstraps the Python project skeleton the other Epics build within.

---

## Problem Statement

There is no code in this repository yet — no package, no tests, no way to reach Ollama.
Without a client that (a) speaks `/api/chat` non-streaming, (b) surfaces the response
fields the loop and transcript need (`message.content`, `message.tool_calls`,
`eval_count`), and (c) converts connection/model failures into typed errors the CLI can map
to exit code 4, neither the execution loop (E1.4) nor the §9 proof (E1.5) can exist.

---

## Goals

By the end of this Epic, the system must:

1. Provide a typed Python client that sends `POST /api/chat` with `stream: false` to a
   configurable endpoint (default `http://localhost:11434`), carrying `model`, `messages`,
   `tools`, and optional `options` (temperature, num_ctx, …)
2. Parse the Ollama response into a typed structure exposing at minimum
   `message.role`, `message.content`, `message.tool_calls` (possibly empty/absent), and
   `eval_count` / `prompt_eval_count` (absent-tolerant) — passing both observed delivery
   modes (§1.2) through verbatim without interpreting them (interpretation is E1.2's job)
3. Raise distinct, typed exceptions for the two runtime-error classes: endpoint
   unreachable/connection failure, and model missing — both mapping to CONTRACT.md exit
   code 4 semantics
4. Contain no invocation of an `ollama` CLI anywhere in the codebase
5. Bootstrap the Python project skeleton (package, test layout, minimal `pyproject.toml`,
   pytest) that E1.2–E1.4 will extend

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Parse or interpret tool calls out of the response (E1.2 — `parse_tool_call`)
- Implement any tool, permission check, loop logic, transcript, or CLI (E1.3, E1.4)
- Support streaming (`stream: true`), retry/backoff, or concurrency (contract non-goals /
  hardening deferred beyond M1)
- Talk to any live Ollama server in its tests — all tests run against recorded/mocked
  responses, no GPU

## Scope of Work

### 1. Project skeleton bootstrap

Create the minimal Python project the rest of M1 builds within.

**Must include:**
- Package directory `local_agent_runner/` with `__init__.py`
- `tests/` directory with pytest wiring (`tests/fixtures/` for recorded responses)
- Minimal `pyproject.toml` (project metadata, dependencies, pytest config) — packaging for
  distribution is out of scope; this exists only so imports and `pytest` work
- A short `README.md` section or docstring stating how to run the tests

### 2. Typed request/response model

**Must include:**
- A `ChatMessage` shape (`role`, `content`, optional `tool_calls`) usable both for request
  `messages` and the response `message`
- A `ChatResponse` shape exposing `message`, `eval_count`, `prompt_eval_count`, and the raw
  response dict (for forward-compatibility); token fields tolerate absence (default `0` or
  `None`, decided and recorded by the Coding Agent)
- Tool definitions accepted as plain dicts in Ollama's `tools` wire format (JSON-schema
  `function` objects) — E1.3 owns producing them

### 3. The client

**Must include:**
- `OllamaClient(endpoint: str = "http://localhost:11434", timeout: float = <generous default>)`
- `chat(model, messages, tools=None, options=None) -> ChatResponse` sending
  `POST {endpoint}/api/chat` with `stream: false` always set
- Configurable per-client HTTP timeout (model inference is slow on a contended GPU; default
  must be generous, e.g. 300 s, and overridable)
- Error mapping:
  - connection refused / DNS failure / timeout → `OllamaConnectionError`
  - HTTP error or Ollama error body indicating the model is not available →
    `OllamaModelMissingError`
  - both subclass a common `OllamaClientError`
- HTTP via `requests` (Epic-level decision: settled here to avoid churn; no `ollama` SDK,
  no CLI)

### 4. Unit tests (mocked — no GPU, no live server)

**Must include:**
- Successful chat round trip: request body verified to contain `model`, `messages`,
  `tools`, `stream: false`
- Both §1.2 response shapes pass through verbatim: a fixture with populated native
  `message.tool_calls` (llama3.1-style) and a fixture with tool-call JSON inside
  `message.content` with empty native field (qwen2.5-coder-style) — the client returns
  them untouched
- `eval_count` / `prompt_eval_count` surfaced when present, tolerated when absent
- Connection failure raises `OllamaConnectionError`
- Model-missing response raises `OllamaModelMissingError`
- Fixtures live in `tests/fixtures/` as recorded/representative Ollama response JSON so
  E1.2 can reuse them

## Definition of Done

Epic E1.1 is complete when:

- [ ] `OllamaClient.chat(...)` sends `POST /api/chat` with `stream: false` to a
      configurable endpoint defaulting to `http://localhost:11434`
- [ ] The typed response exposes `message.content`, `message.tool_calls`, `eval_count`,
      and `prompt_eval_count`, tolerating absent token fields
- [ ] `OllamaConnectionError` and `OllamaModelMissingError` are raised for their respective
      failure classes and share a common base
- [ ] `grep`-verifiable: no `ollama` CLI invocation exists anywhere in the codebase
- [ ] All unit tests pass via `pytest` with no live Ollama server and no GPU
- [ ] Both delivery-mode fixtures exist under `tests/fixtures/` and are exercised by tests
- [ ] Delivery Notice produced and committed
- [ ] All changes committed to `epic/E1.1` branch, delivered for merge to `milestone/M1`

---

## Acceptance Criteria

- [ ] E1.4 (execution loop) can drive one model turn through this client using only its
      public surface: construct client → `chat(model, messages, tools)` → read
      `message` and `eval_count` from the result
- [ ] A connection failure or missing model is distinguishable by exception type alone,
      sufficient for the CLI to emit exit code 4 with a one-line reason
- [ ] Tests run green in a fresh clone with `pip install` + `pytest` and nothing else (no
      Ollama, no Docker, no GPU)
- [ ] The recorded fixtures faithfully represent both §1.2 delivery modes (native
      `tool_calls` populated; content-embedded JSON with empty native field)

## Technical Constraints

**Language:** Python (Milestone-level decision)
**HTTP:** `requests`; never the `ollama` CLI or SDK
**Endpoint:** configurable; default `http://localhost:11434`; `stream: false` always
**Testing:** pytest; mocked/recorded responses only — no GPU, no live server
**Environment:** must run inside a container (CONTRACT.md §10.3); no host-specific paths

## Execution Notes

- Start from an empty codebase: skeleton first, then shapes, then client, then tests.
- Do not interpret responses — if `tool_calls` is empty and `content` holds a JSON blob,
  return it as-is. E1.2 owns extraction.
- Record in the Delivery Notice any absent-field defaults you settle (e.g. `eval_count`
  when Ollama omits it).
- Fixtures should mirror Ollama's real `/api/chat` non-streaming response shape
  (`model`, `created_at`, `message`, `done`, `eval_count`, `prompt_eval_count`, …) so
  they remain reusable by E1.2.
