# Epic E1.2 — Tool-Call Parser & Argument Coercion

## Context

E1.1 delivered the typed Ollama client and the project skeleton; it is merged to
`milestone/M1`. The client is deliberately interpretation-free: responses pass through
verbatim, in whichever of the two observed delivery modes the model used
(CONTRACT.md §1.2 — populated native `message.tool_calls` for llama3.1-class models;
tool-call JSON embedded in `message.content` with an empty native field for
qwen2.5-coder, the default model).

This Epic builds `parse_tool_call` — named by the Milestone spec as **the engine's crux**
— plus the JSON-schema argument coercion of §1.3 (llama3.1 was observed serializing
integers as strings, e.g. `"8"`). E1.1's recorded fixtures already carry both delivery
modes and the mistyped-integer case, specifically so this Epic can test against them.

E1.2 was planned as mutually independent of E1.1/E1.3; with E1.1 now merged, it builds in
the existing skeleton and reuses its fixtures, but it must not require a live client — it
operates on response *messages*, not on HTTP.

---

## Problem Statement

The loop (E1.4) cannot exist without a single, well-tested answer to: *given a model
response, what did the model just do?* There are four materially different answers —
a valid tool call, a final answer, a repairable mistake (unknown tool, invalid/missing
arguments), or a mistyped-but-fixable call — and §5 routes each differently. If this
classification is wrong or untested, the loop either crashes where it should repair or
terminates where it should act. This is the project's founding risk in code form.

---

## Goals

By the end of this Epic, the system must:

1. Provide `parse_tool_call` implementing CONTRACT.md §5 exactly: native
   `message.tool_calls` first; else extract a tool-call JSON from `message.content`
   (```json fence or bare `{"name": ..., "arguments": {...}}` object); else final answer
2. Classify outcomes into three distinguishable results the loop can route on: **tool
   call** (name + coerced arguments), **final answer**, or **repairable error** with a
   model-facing message (unknown tool; invalid, missing, or uncoercible arguments)
3. Coerce mistyped primitive arguments against the tool's JSON schema (§1.3) —
   string-encoded integers at minimum, plus number/boolean/string — before execution
4. Validate calls against the enabled tool definitions (Ollama wire format, the same
   dicts E1.1's `chat(tools=...)` accepts and E1.3 will produce)
5. Prove all of it with offline unit tests over both delivery modes, reusing E1.1's
   recorded fixtures and adding edge-case fixtures of its own

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Execute tools, check permissions, or produce tool results (E1.3)
- Run the loop, build repair messages into the conversation, or emit transcripts (E1.4 —
  this Epic *classifies*; the loop *routes*)
- Handle streaming responses or delivery modes beyond the two observed in §1.2
- Coerce nested/complex schema types — the three proof tools have flat schemas of
  primitives; nested coercion is hardening beyond M1

## Scope of Work

### 1. Parse result model

A small typed result the loop can route on without string-matching.

**Must include:**
- `ToolCallRequest` — `name: str`, `arguments: dict` (post-coercion)
- `FinalAnswer` — carries the answer text (`message.content`)
- `RepairableError` — carries a clear, model-facing error message (this becomes the tool
  result fed back in §5's repair loop) and a machine-readable reason kind (e.g.
  `unknown_tool`, `invalid_arguments`)
- These three are the complete, closed set of outcomes

### 2. `parse_tool_call`

`parse_tool_call(message, tools) -> ToolCallRequest | FinalAnswer | RepairableError`
in `local_agent_runner/tool_calls.py`, where `message` is a response message (E1.1's
`ChatMessage` or the equivalent plain dict) and `tools` are enabled tool definitions in
Ollama wire format.

**Must include:**
- Native mode: `message.tool_calls` non-empty → use the **first** call (multiple calls:
  first-only for M1, settled below)
- Content mode: `tool_calls` empty/absent → scan `message.content` for a ```json fence
  (with or without surrounding prose) or a bare `{"name": ..., "arguments": {...}}`
  object as the whole (stripped) content
- Step 4 of §5's parse contract: nothing parseable → `FinalAnswer(content)`. This
  includes a fence whose body is not valid JSON — unparseable text is an answer, not an
  error
- A well-formed call whose `name` is not among the enabled tools → `RepairableError`
  (`unknown_tool`) naming the tool and listing the enabled ones
- A well-formed call with missing required arguments, unknown argument keys tolerated or
  rejected per schema, or arguments that fail coercion → `RepairableError`
  (`invalid_arguments`) saying exactly what is wrong

### 3. Argument coercion

`coerce_arguments(arguments, json_schema) -> dict` (also in `tool_calls.py`), applied by
`parse_tool_call` before returning a `ToolCallRequest`; independently callable and
independently tested.

**Must include:**
- `"8"` → `8` for `integer` properties (the §1.3 observed case); analogous string→
  `number` and string→`boolean` (`"true"`/`"false"`, case-insensitive) coercions
- Already-correct types pass through unchanged; `string` properties never coerced
- Uncoercible values (`"abc"` for an `integer`) raise/return the `invalid_arguments`
  repair outcome — never a crash
- Missing **required** properties (per the schema's `required` list) → `invalid_arguments`
- Properties not in the schema pass through untouched (the tool handler decides; M1
  schemas are flat and permissive)

### 4. Unit tests (offline — no GPU, no live server, no HTTP)

`tests/test_tool_calls.py`, with new edge-case fixtures added under `tests/fixtures/`.

**Must include:**
- Native mode via E1.1's `chat_native_tool_calls.json` — parses to `read_file` and
  coerces `"start_line": "8"` → `8` against a read_file-shaped schema
- Content mode via E1.1's `chat_content_embedded_tool_call.json` — fence extracted,
  parsed, validated
- Final answer via E1.1's `chat_final_answer.json` — returns `FinalAnswer`
- New fixtures/cases: bare JSON object as whole content; fence surrounded by prose;
  fence with invalid JSON (→ `FinalAnswer`); well-formed call with unknown tool name
  (→ `RepairableError(unknown_tool)`); missing required argument; uncoercible argument
- Direct `coerce_arguments` tests: each primitive coercion, pass-through, and failure

## Definition of Done

Epic E1.2 is complete when:

- [ ] `parse_tool_call` returns the native call when `message.tool_calls` is non-empty,
      without touching `content`
- [ ] `parse_tool_call` extracts a content-embedded call from a ```json fence and from a
      bare JSON object, when the native field is empty or absent
- [ ] Nothing-parseable content (including invalid JSON in a fence) yields `FinalAnswer`
- [ ] Unknown tool and invalid/missing/uncoercible arguments yield `RepairableError` with
      a model-facing message and machine-readable kind
- [ ] `coerce_arguments` fixes string-encoded integers, numbers, and booleans against the
      schema; passes correct types through; reports uncoercible values as
      `invalid_arguments`
- [ ] All unit tests pass via `pytest` offline; E1.1's three chat fixtures are reused,
      unmodified
- [ ] No `ollama` CLI invocation introduced anywhere
- [ ] Delivery Notice produced and committed
- [ ] All changes committed to `epic/E1.2` branch, delivered for merge to `milestone/M1`

## Execution Notes

- Implement `coerce_arguments` first (small, closed problem), then the result types,
  then `parse_tool_call`, then the fixture-driven tests.
- The §5 boundary to keep sharp: *unparseable* → final answer; *parseable but wrong* →
  repairable error. Do not blur these — the loop's termination correctness depends on it.
- Error messages in `RepairableError` are read by a local model mid-repair-loop: state
  what was wrong and what valid looks like, in one or two short sentences.
- Record in the Delivery Notice any robustness you add beyond the two specified content
  forms (e.g. best-effort extraction of a bare object embedded in prose), and keep such
  extras strictly additive.

## Notes

- Epic-level decisions settled in this spec (do not reopen without a spec amendment):
  - **Multiple native tool calls: first-only for M1.** The contract permits queuing;
    M1's proof needs one call per turn. Queuing is deferred hardening.
  - **Invalid JSON in a fence is a final answer**, per the letter of §5 step 4
    ("nothing parseable"), not a repairable error.
  - **Closed three-variant result model** (`ToolCallRequest` / `FinalAnswer` /
    `RepairableError`) — the loop routes on types, never on strings.
  - **Coercion scope:** flat primitive schemas only (integer, number, boolean, string);
    nested coercion deferred beyond M1.
