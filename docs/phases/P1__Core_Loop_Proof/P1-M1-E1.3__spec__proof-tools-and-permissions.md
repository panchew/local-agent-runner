# Epic E1.3 — Proof Tools & Permission Scoping

## Context

E1.1 (Ollama client, project skeleton) and E1.2 (`parse_tool_call`, argument coercion)
are merged to `milestone/M1`. The engine can now talk to a model and classify what the
model did — but a valid `ToolCallRequest` still has nothing to execute against.

This Epic delivers the three proof tools CONTRACT.md §9 needs — `read_file`, `edit_file`,
`run_command` — with the §4 permission knobs the proof requires: `allow_paths` globs for
the file tools; `allow_commands`/`deny_commands` patterns and `timeout` for
`run_command`. A local model running `run_command` is powerful; permissions are the
guardrail (the container, per §10.3, is the outer line of defense — the permission layer
is the second, not the only one).

Everything a tool does wrong — denied path, missing file, ambiguous edit, denied or
timed-out command, unexpected exception — must come back as a **deterministic,
model-facing error result**, because §5's repair loop feeds tool errors back to the model
rather than crashing.

---

## Problem Statement

The remaining gap between "parsed call" and "running loop" is execution: there are no
tool definitions to send to the model, no handlers to run, and no permission enforcement.
Without deterministic, permission-scoped tools, E1.4 cannot wire the loop and E1.5's
proof (read a file → edit one line → run a test) has nothing to drive. An unguarded
`run_command` would also violate the contract's safety posture.

---

## Goals

By the end of this Epic, the system must:

1. Provide Ollama wire-format definitions (JSON-schema `function` objects) for
   `read_file`, `edit_file`, and `run_command` — the same dicts E1.1's `chat(tools=...)`
   sends and E1.2's `parse_tool_call(tools=...)` validates against
2. Implement the three handlers with the §4 argument shapes:
   `read_file(path, start_line?, end_line?)`, `edit_file(path, old, new)`,
   `run_command(command)`
3. Enforce permissions parsed from the §4 `tools.json` shape: `allow_paths` globs for
   file tools; `allow_commands` patterns, `deny_commands` patterns, and `timeout`
   seconds for `run_command` — **deny by default** when a knob is absent
4. Return every expected failure (denial, missing file, ambiguous edit, timeout,
   non-zero exit is *not* a failure — see Scope) as a deterministic error string in a
   `ToolResult`; `execute_tool` never raises
5. Prove all of it with offline unit tests (temp dirs and innocuous commands — no GPU,
   no Ollama, no network)

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Ship `write_file`, `list_dir`, or `git` tools, or the full §4 permission model beyond
  what the three proof tools need
- Run the loop, feed errors back to the model, or emit transcripts (E1.4 routes;
  this Epic only produces results)
- Load `tools.json` from disk or parse CLI flags (E1.4 — this Epic exposes
  `from_dict`-style construction only)
- Sandbox beyond the permission layer (the container is §10.3's concern, not code in
  this Epic)
- Support custom/pluggable tool handlers (library interface, deferred beyond M1)

## Scope of Work

### 1. Permissions model

`ToolPermissions` in `local_agent_runner/tools.py`, constructed from the §4 `tools.json`
dict shape (`enabled`, `allow_paths`, `allow_commands`, `deny_commands`, `timeout`).

**Must include:**
- `from_dict(data) -> ToolPermissions` (file I/O stays in E1.4)
- `allow_paths`: list of globs. A path is permitted iff its **resolved absolute path**
  (symlinks and `..` resolved first — traversal must not escape) matches at least one
  glob. Absent/empty list → all paths denied
- `allow_commands` / `deny_commands`: `fnmatch`-style patterns matched against the whole
  command string. Permitted iff it matches an allow pattern **and** no deny pattern
  (deny wins). Absent/empty `allow_commands` → all commands denied
- `timeout`: seconds for `run_command`; a sane default (e.g. 120, per the §4 example) if
  absent
- `enabled`: the tool subset exposed to the model; `tool_definitions(permissions)`
  returns definitions only for enabled tools

### 2. Tool definitions

Wire-format definitions for the three tools with flat primitive JSON schemas (E1.2's
coercion scope), `required` lists set correctly (`path` for `read_file`;
`path`/`old`/`new` for `edit_file`; `command` for `run_command`), and descriptions
written for a local model (short, imperative, stating what valid arguments look like).

### 3. The three handlers + execution surface

`execute_tool(name, arguments, permissions) -> ToolResult` where
`ToolResult(ok: bool, output: str)` — `output` is exactly the text fed back to the model
as the tool result (E1.4 passes it through verbatim).

**Must include:**
- `read_file`: returns file content; optional `start_line`/`end_line` (1-based,
  inclusive) slice; denied path / missing file / bad range → error result
- `edit_file`: `old` must occur **exactly once** in the file; replaces it with `new` and
  writes back. Not found and ambiguous (>1 occurrence) are distinct deterministic
  errors; denied path / missing file → error result
- `run_command`: runs the command via `subprocess` with the enforced timeout,
  `shell=True` (settled below), capturing stdout/stderr. Output reports exit code,
  stdout, and stderr in a fixed format; **non-zero exit is `ok=True`** — a failing test
  is information for the model, not a tool failure. Denied command and timeout → error
  result. Output capped (fixed cap with truncation marker — token discipline, §6)
- Unknown tool name at execution time and any unexpected handler exception → error
  result with a deterministic message; `execute_tool` never raises
- Error messages are model-facing: state what was denied/wrong and what permitted looks
  like, one or two short sentences, stable wording (deterministic per §4 — same denial,
  same message)

### 4. Unit tests (offline — no GPU, no Ollama, no network)

`tests/test_tools.py`, using pytest `tmp_path` and innocuous commands
(`echo`, `python3 -c ...`, a sleep for the timeout case).

**Must include:**
- `read_file`: full read; line-range read; path outside `allow_paths` denied; `..`
  traversal that resolves outside allowed globs denied; missing file
- `edit_file`: successful single replacement (content verified on disk); `old` not
  found; `old` ambiguous; denied path
- `run_command`: allowed command runs (stdout captured, exit code reported); non-zero
  exit returned as `ok=True` with the code visible; command matching no allow pattern
  denied; command matching a deny pattern denied even when allowed; timeout kills and
  returns an error result; output cap enforced
- Permissions: deny-by-default for both knobs; `from_dict` on the §4 example shape;
  `tool_definitions` filtered by `enabled`
- Determinism: the same denial twice yields byte-identical messages
- Integration seam: an E1.2 `ToolCallRequest` for each tool executes through
  `execute_tool` using only public surfaces

## Technical Constraints

**Language:** Python; module `local_agent_runner/tools.py` in the existing skeleton
**Command execution:** `subprocess.run` with `shell=True` and enforced timeout (settled
below); never the `ollama` CLI
**Path matching:** globs against resolved absolute paths (`fnmatch`/`pathlib`);
traversal-safe
**Testing:** pytest, fully offline; `tmp_path` fixtures; innocuous commands only
**Environment:** must run inside a container (CONTRACT.md §10.3); no host-specific paths

## Notes

- Epic-level decisions settled in this spec (do not reopen without a spec amendment):
  - **`shell=True` for `run_command`.** The §4 guardrails are the allow/deny patterns
    and the container (§10.3); shell execution keeps observed model behavior working
    (e.g. `python -m pytest test_x.py`). Compound commands are governed by the same
    pattern matching.
  - **Deny by default** for both `allow_paths` and `allow_commands`.
  - **Non-zero exit codes are successful tool results** — a failing test is what the
    §9 proof model must be able to observe and react to.
  - **`edit_file` requires exactly one occurrence of `old`** — not-found and ambiguous
    are distinct repairable errors; deterministic edits over convenient ones.
  - **`execute_tool` never raises** — the §5 "handler exception → tool_error" conversion
    lives here, not in the loop.
