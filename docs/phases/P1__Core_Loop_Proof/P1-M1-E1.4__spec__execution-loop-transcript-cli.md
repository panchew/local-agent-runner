# Epic E1.4 — Execution Loop, Transcript & CLI

## Context

All three foundation Epics are merged to `milestone/M1`: E1.1 (typed Ollama client),
E1.2 (`parse_tool_call` + coercion, closed three-variant result), E1.3 (the three proof
tools behind a never-raising `execute_tool`, §4 permissions). Each piece is unit-proven
offline; none of them runs anything yet.

This Epic is the assembly: the CONTRACT.md §5 execution loop that wires
`chat → parse_tool_call → execute_tool → feed back` until the model produces a final
answer or the iteration ceiling halts it; the §3 Result/transcript with token
accounting; and the §2 CLI with exit codes 0/2/3/4. When this Epic is done, the engine
is invocable end-to-end — E1.5 only points it at a live model.

The seams were designed for this assembly: `ChatResponse.message` feeds
`parse_tool_call` directly; the parser's three outcome types are routed without string
inspection; `RepairableError.message` and `ToolResult.output` are both ready-to-feed-back
tool results; `tool_definitions(permissions)` produces the dicts both `chat(tools=...)`
and `parse_tool_call(tools=...)` consume.

---

## Problem Statement

The engine's parts exist but there is no engine: nothing maintains the message history,
routes parse outcomes, feeds errors back instead of crashing, enforces the iteration
ceiling, records what happened, or maps outcomes to the §2 exit codes the future
orchestrator (and E1.5's proof harness) depends on. Until this Epic lands, the §9 proof
cannot even be attempted.

---

## Goals

By the end of this Epic, the system must:

1. Run the §5 loop exactly: `messages = [system?, context?, user(task)]`; at most
   `max_iterations` model turns; a turn with no tool call terminates as the final
   answer; tool calls execute and their results append to the history; every
   repairable condition (malformed call, unknown tool, invalid arguments, denied
   permission, handler failure) feeds back as a tool result — repair, don't crash
2. Terminate deterministically: final answer → `completed`; ceiling reached →
   `max_iterations_exceeded` (default ceiling 10); client failure mid-run → `error`
3. Emit the §3 Result: `status`, `final_answer`, ordered `transcript` steps
   (`tool_call:{name,args}`, `tool_result`, `ms`, `eval_count`), `iterations`, total
   `tokens`, `model`, `duration_ms` — written as JSON to `--transcript`
4. Provide the §2 CLI: `--model` (default `qwen2.5-coder:14b`), `--task` / `--task-text`,
   `--tools`, `--max-iterations` (default 10), `--endpoint` (default
   `http://localhost:11434`), `--transcript`; exit codes `0` completed, `2`
   did-not-converge, `3` config/tool error, `4` runtime error; one-line stderr reason on
   every non-zero exit
5. Prove all of it offline with a scripted fake client (recorded/mocked turn sequences)
   — no GPU, no live server

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Run against a live model or touch the GPU (E1.5)
- Expose `--context` / `--system` CLI flags (the library loop accepts optional
  system/context texts per §5's message shape, but the CLI surfaces only the milestone's
  goal-7 flag set; exposing more is deferred until the proof demands it)
- Provide the public library entry point with pluggable custom tool handlers (deferred
  beyond M1)
- Add retry/backoff, streaming, concurrency, or multi-model validation (hardening,
  deferred)
- Build the governance adapter or any UI (later phases)

## Scope of Work

### 1. The loop (`local_agent_runner/loop.py`)

`run(model, task, permissions, *, endpoint=..., max_iterations=10, system=None,
context=None, options=None, client=None) -> Result` — `client` injectable for tests.

**Must include:**
- Message seeding per §5: optional system message, optional context message (as a
  system-role message), then `user(task)`
- Per turn: `chat(model, messages, tools=tool_definitions(permissions))` →
  `parse_tool_call(response.message, tools)` → route by type:
  - `FinalAnswer` → return `completed` with `final_answer`
  - `ToolCallRequest` → `execute_tool(...)`; append the assistant message (as returned
    by the model) and a `role: "tool"` message whose content is `ToolResult.output`
    (ok or not — a tool-level error is §5 repair feedback, not a crash)
  - `RepairableError` → append the assistant message and a `role: "tool"` message
    whose content is the error's model-facing `message`
- At most `max_iterations` turns total (§5 pseudocode: `for i in 1..max_iterations`);
  loop exhaustion → `max_iterations_exceeded`
- `OllamaClientError` during any turn → `status: "error"` Result carrying the reason
  (the CLI maps it to exit 4); no partial crash — whatever transcript accumulated is
  preserved
- No permission logic, no parsing logic, no tool logic in the loop — it routes;
  E1.2/E1.3 decide

### 2. Result & transcript (`local_agent_runner/loop.py`)

**Must include:**
- `Result` with the §3 fields: `status` (`completed` | `max_iterations_exceeded` |
  `error`), `final_answer`, `transcript`, `iterations`, `tokens`, `model`,
  `duration_ms`; `to_dict()` produces the exact §3 JSON shape
- One transcript step per tool round (executed call *or* repair round):
  `{"tool_call": {"name": ..., "args": ...}, "tool_result": <text fed back>,
  "ms": <wall ms of the round>, "eval_count": <response eval_count>}`. For repair
  rounds, `name`/`args` record what the model attempted (the unknown tool's name, the
  uncoercible arguments); a turn ending in a final answer adds no step
- `iterations` = number of tool rounds executed (transcript length); `tokens` = sum of
  per-turn `eval_count` over **all** turns including the final one (`None` counted as
  0); `duration_ms` = wall time of the whole run
- The final-answer turn's `eval_count` must not be lost: record it in `tokens` (this is
  §6's cost-visibility requirement)

### 3. CLI (`local_agent_runner/cli.py`, `__main__.py`, console script)

**Must include:**
- Flags per Goal 4, defaults per CONTRACT.md §2; exactly one of `--task` (file path,
  content read as the task text) / `--task-text` required
- `--tools` = path to a §4-shaped `tools.json`; parsed via
  `ToolPermissions.from_dict`; a name in `enabled` that is not a known tool is a
  **config error** (exit 3) at startup — config-time strictness, distinct from the
  model's runtime unknown-tool repair
- Exit-code mapping: `completed` → 0; `max_iterations_exceeded` → 2; config/tool errors
  (bad flags, unreadable/invalid task, tools.json, unwritable transcript path, unknown
  enabled tool) → 3; `OllamaClientError` and any unexpected exception → 4
- One-line reason on stderr for every non-zero exit; `final_answer` printed to stdout
  on success
- `--transcript <path>`: Result JSON written on every run that reaches the loop
  (including status `error` — best effort), so failed runs are inspectable
- Console script `local-agent-runner` (pyproject `[project.scripts]`) and
  `python -m local_agent_runner` both work

### 4. Unit tests (offline — no GPU, no Ollama, no network)

`tests/test_loop.py`, `tests/test_cli.py`; a scripted fake client returning a
programmed sequence of `ChatResponse`s (built from the recorded fixtures where they
fit).

**Must include (loop):**
- Immediate final answer → `completed`, empty transcript, `iterations == 0`, tokens
  counted
- Tool call then final answer → one step with `tool_result == ToolResult.output`, `ms`
  and `eval_count` populated, tokens = sum over both turns
- Repair paths, one test each, all converging afterwards: content-mode malformed-then-
  valid; unknown tool; invalid/uncoercible arguments; denied permission
  (`ToolResult.ok == False` fed back); the §5 milestone AC quartet
- Termination: model that never stops calling tools → exactly `max_iterations` turns,
  `max_iterations_exceeded`, transcript length == ceiling
- Client raises `OllamaConnectionError` mid-run → `status == "error"`, prior steps
  preserved
- Native and content delivery modes both drive the loop (fixture-shaped responses)

**Must include (CLI):**
- Exit code 0 with final answer on stdout; transcript JSON written and §3-shape-valid
  (all seven keys, step keys exact)
- Exit code 2 on ceiling exhaustion; transcript still written
- Exit code 3: missing `--task`/`--task-text`, unreadable task file, invalid
  tools.json, unknown enabled tool — one-line stderr each
- Exit code 4: connection error (fake client injection or unreachable localhost port)
  — one-line stderr; transcript with `status: "error"` written when the loop was
  reached
- `--max-iterations` and `--endpoint` reach the loop/client (observable via the fake)

- [ ] The loop routes all three parse outcomes and both delivery modes; repairs on
      malformed call, unknown tool, invalid arguments, denied permission, and handler
      failure; and always halts (final answer or ceiling)

      `transcript` steps with `tool_call:{name,args}` / `tool_result` / `ms` /
      `eval_count`, `iterations`, `tokens`, `model`, `duration_ms`

      reaches the loop

      one-line stderr reason
- [ ] `local-agent-runner` (console script) and `python -m local_agent_runner` both
      invoke the CLI
- [ ] All unit tests pass via `pytest` offline; no `ollama` CLI invocation anywhere

## Execution Notes

- Build order: `Result`/transcript shape → loop with the fake client and tests →
  CLI over the loop → CLI tests. The loop is the §5 pseudocode almost line for line —
  keep it that recognizable.
- Message-history fidelity: append the assistant message **as the model produced it**
  (native `tool_calls` intact, or content JSON as content) before the `role: "tool"`
  feedback — the model must see its own prior turn the way it emitted it.
- Record in the Delivery Notice: the exact assistant/tool message shapes appended in
  each mode, the `status: "error"` transcript's field values (`final_answer` null or
  empty — your call, recorded), and any stderr reason-format convention.
- Do not print the transcript to stdout; stdout is the final answer only (§2's
  file-based I/O discipline).

## Notes

- Epic-level decisions settled in this spec (do not reopen without a spec amendment):
  - **`iterations` = tool rounds executed** (= transcript length); an immediate final
    answer is `iterations: 0`. `max_iterations` bounds total model turns per the §5
    pseudocode.
  - **Repair rounds are transcript steps** — they consume iterations and are visible
    (a "clean transcript" in E1.5 means, among other things, no repair steps in the
    final iteration; the §9 acceptance depends on repairs being observable).
  - **CLI surfaces only the goal-7 flag set**; `run(...)` accepts `system`/`context`
    texts so a flag can be added later without loop changes.
  - **Unknown tool name in `enabled` is a config error (exit 3)** at CLI startup;
    the runtime unknown-tool repair path is for the *model's* mistakes, not the
    caller's.
  - **Transcript is written even for `error` and `max_iterations_exceeded` runs** —
    failed runs must be inspectable (§6 cost visibility, E1.5 debugging).
