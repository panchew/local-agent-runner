# Epic E4.2: Pluggable custom tool handlers (`custom_tools`)

> **About this spec.** It was written *after* execution. It records the scope as it was
> requested, in three successive increments (see Scope of Work), so that the Delivery Notice
> has a Definition of Done to verify against. The Epic ID `E4.2` is **provisional**: it
> follows E4.1, which explicitly deferred this slice, and needs to be confirmed by the
> Milestone/HQ Chat.

## Context

CF-2 ("library entry point `run(...) -> Result` with pluggable custom tool handlers") was
deferred at P2 closure. E4.1 delivered the first half: `run` and `Result` are exported from the
package root. Its spec explicitly deferred the second half: *"Pluggable custom tool handlers,
the second half of CF-2, are a later slice."*

CONTRACT.md already settles the design direction:

- **§2:** the library entry point is the interface "for callers that want to register custom
  in-process tool handlers".
- **§4:** the CLI exposes only the vetted built-in library, and "custom/non-coding tools are
  registered through the library interface".
- **§10.1:** built-in library for the CLI **and** pluggable handlers for the library, both.

What doesn't exist yet is the mechanism itself. `run()` only knows the built-in table
(`tool_definitions(permissions)` plus `execute_tool()`).

## Problem Statement

A library caller can't give the model a tool of their own. Every tool name the model may call
is hard-wired in `tools.py`. The contract promises pluggable handlers but doesn't define their
interface.

## Goals

1. A caller can turn a plain typed Python function into a tool and pass it to `run()`.
2. Custom tools behave exactly like built-ins inside the §5 loop: the same parsing (native and
   content modes, §1.2), argument coercion (§1.3) and repair-don't-crash handling.
3. Several custom tools can be registered together without conflict, and alongside enabled
   built-ins.
4. A custom tool that calls an external service is shown to be achievable **safely**. It is
   verified for security, idempotency and integrity, and the results are tracked.

## Non-Goals

- No custom tools on the CLI path. §4 keeps the CLI to the vetted built-ins.
- No change to existing behavior when `custom_tools` isn't passed.
- No permission model for custom tools. Enabling one means registering it, and scoping is the
  caller's responsibility.
- No schema inference beyond flat primitives (`str`/`int`/`float`/`bool`, the §1.3 scope).
- No version bump. That's a phase-closure concern.

## Scope of Work

**Increment 1: the mechanism plus a proving tool** (request: *"a tool method, a simple
`hello_world`… a proven functionality to add custom_tool"*)
- `local_agent_runner/custom_tools.py` contains `CustomTool`, `@custom_tool` (schema inferred
  from the signature, description from the docstring), registration validation and a
  never-raising executor.
- `run(..., custom_tools=...)` in `loop.py`: custom definitions are merged after the enabled
  built-ins, and calls are routed by name.
- Public exports: `custom_tool`, `CustomTool`, `ToolResult`.
- `examples/hello_world_tool.py` (tool plus live-proof script) and offline tests.

**Increment 2: coexistence** (request: *"a second custom tool to verify that it does not
conflict with the first"*)
- `examples/goodbye_world_tool.py` is a near-twin of `hello_world` with the **same argument
  name**, so routing has to go by tool name. It's paired with `examples/multi_tool_proof.py`.
- Offline tests cover routing, ordering, isolation, failure isolation and the absence of a
  global registry.

**Increment 3: an external-service tool and tracked verification** (request: *"a custom tool
that makes an external request to a fake 3rd party service and verify security, idempotency
and integrity… keep track of the results"*)
- `examples/ticket_service/` contains:
  - the reference tool (`create_ticket`, `get_ticket`)
  - a fake third-party API over real HTTP with fault injection
  - a live-model proof script
- `tests/test_ticket_service_tool.py` holds the tracked checks (`SEC-*`, `IDEM-*`, `INT-*`).
- `tests/conftest.py` provides opt-in result tracking (`--verification-report`).
- `proof/custom_tool_mutation_check.py` shows that every protection is covered by a check.
- `proof/run-custom-tool-verification.sh` runs it all with one command, and results go to
  `proof/artifacts/custom-tools/ticket-service/`.

**Increment 4: documentation** (request: *"document the work we are going to deliver"*)
- CONTRACT §4.1, README, this spec and the Delivery Notice.

## Definition of Done

1. `from local_agent_runner import custom_tool, CustomTool, ToolResult` works.
2. A `@custom_tool` function passed via `run(..., custom_tools=[...])` is offered to the model,
   executed when called, and its output is fed back as the tool result. This holds in both §1.2
   delivery modes.
3. Custom tool arguments are coerced against the inferred schema. A missing or bad argument, or
   a handler exception, becomes repair feedback, never a crash.
4. A name that collides with a built-in, or a duplicate name, raises `ValueError` before the
   first model call.
5. `run()` without `custom_tools` behaves exactly as before, and all pre-existing tests pass
   unchanged.
6. Two custom tools that share an argument name are each routed to their own handler, in any
   registration order, alongside built-ins, with no state bleeding between them. A tool that
   isn't registered isn't offered.
7. The external-service tool passes every tracked security, idempotency and integrity check.
8. Every protection in the external-service tool is caught by at least one check when it's
   disabled (mutation check: 0 survivors).
9. Results are written to a tracked location, with per-check evidence and a per-run history.
10. The full suite passes offline. A fresh clone with the delivered file set passes it too.
11. CONTRACT, README, spec and Delivery Notice document the delivered interface and evidence.
12. The live-model proof runs on the host against Ollama (`LIVE=1`). *This requires the host
    GPU and Ollama, so it can't be done in the execution environment.*

## Acceptance Criteria

- `pytest` passes fully offline, with no new runtime dependency (`requests` was already one).
- `proof/run-custom-tool-verification.sh` prints `VERIFICATION: PASS`.
- `verification-results.md` shows 0 failed checks, and `mutation-results.md` shows 0 survivors.
- The CLI (`cli.py`) and the built-in tool library (`tools.py`) are unmodified.
