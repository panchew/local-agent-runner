# Epic E3.1 — CONTRACT §7 Runner-Side Adapter Verification

## Context

M2 closed the runner's tool surface (E2.1/E2.2) and the SN-3 repair nudge (E2.3), all
merged to `phase/P2` at `0e1b802`. What remains before the adapter shim
(`bin/run-dev-agent`, CONTRACT.md §7) has anything real to integrate against is a single
CLI gap: `run()` already accepts a `context` parameter (§5 — seeds an optional leading
system-role message) but the CLI never surfaces it (P1 explicitly deferred this: "the
CLI does not surface them in M1", per `run()`'s own docstring in
`local_agent_runner/loop.py`). This Epic closes that gap and proves — offline, against a
fixture that reproduces the shim's documented invocation shape exactly — that the
runner's exit codes and `--transcript` JSON are the adapter's complete, sufficient
success/failure signal, without ever reading `final_answer` (SN-3).

---

## Problem Statement

CONTRACT.md §7 step 2 specifies the shim builds a Task as: `--task` = the epic's
Definition of Done text, `--context` = the scoped epic spec/starter (never full
governance), `--tools` = the coding set scoped to a repo, `--model` = the active tag from
`AI_PROJECT_ACTIVE_MODEL`. Two things are unverified today:

1. `--context` doesn't exist on the CLI at all — `_load_task`/`build_parser` in
   `local_agent_runner/cli.py` has no equivalent for it, so the shim's step 2 cannot be
   reproduced end-to-end through the CLI, only through the library `run()` call directly.
2. Nothing currently proves that this *exact* invocation shape — DoD-shaped task,
   scoped-context system message, a coding-set `tools.json`, an explicit model tag —
   converges to a stable, adapter-consumable result using only exit code and transcript.
   The existing CLI test suite (`tests/test_cli.py`) covers the CLI's mechanics
   generically; it does not target the shim's specific invocation pattern as a named
   scenario.

Both gaps block E3.2 (the live run): the adapter Epic on the ai-project-system side
(SN-4, out of this project's governance) needs a runner-side contract that is both
complete (the flag exists) and proven (the fixture demonstrates it holds).

---

## Goals

By the end of this Epic, the system must:

1. Expose `--context` on the CLI: an optional flag that reads a file whose content is
   passed through unchanged to `run()`'s existing `context` parameter — mirroring how
   `--task` already reads a file into the `task` parameter
2. Reproduce CONTRACT.md §7 step 2's exact invocation pattern in an offline fixture: a
   DoD-shaped `--task`, a scoped epic-spec/starter-shaped `--context`, a coding-set
   `--tools` (the §4 built-in set, scoped to a repo via `allow_paths`), and an explicit
   `--model` tag — run end-to-end through the CLI (`main()`, scripted `FakeClient`, no
   GPU, no Ollama, no network)
3. Demonstrate, against that fixture, that success is fully determined by exit code
   (`0`) plus the `--transcript` §3 Result JSON's structural shape — never by reading or
   asserting on `final_answer`'s content (SN-3: consumers MUST NOT depend on
   `final_answer`)
4. Demonstrate, against the same fixture shape, that the other three exit codes the
   adapter must handle (`2` did-not-converge, `3` config error, `4` runtime error) are
   unchanged from M2 behavior and remain reachable and stable under this exact
   invocation pattern
5. Cover `--context`'s wiring with a unit test that confirms the file's content reaches
   the model as a system-role message ahead of the task message (per §5's existing
   `context`-then-`task` message order in `run()`) — not just that the CLI accepts the
   flag

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Build `bin/run-dev-agent` or any part of the adapter shim itself — that is Epic-shaped
  work inside ai-project-system's own governance (SN-4); this Epic delivers only the
  runner-side flag and its offline proof
- Expose `--system` on the CLI — out of scope per the Milestone spec's scope-narrowing
  decision (the §7 shim's invocation pattern does not use it)
- Add a `--context-text` companion flag — CONTRACT.md §2's documented CLI surface shows
  a single file-based `--context context.md`, not a mutually-exclusive text/file pair
  like `--task`/`--task-text`; adding one would be surface beyond what §7's invocation
  pattern or §2 calls for
- Touch `final_answer` handling, the SN-3 repair nudge (`_is_unusable_final_answer`,
  `_request_plain_answer`), or any part of `loop.py`'s execution loop — `run()`'s
  `context` parameter already exists and is untouched by this Epic; only the CLI grows a
  flag that feeds it
- Execute a live run against Ollama or GPU hardware — E3.1 is fully offline and
  fixture-based; the live run is E3.2
- Change exit code values, `Result`/§3 field names, or any part of the transcript shape
  — this Epic verifies stability, it does not modify the contract

## Scope of Work

### 1. `--context` CLI flag

In `local_agent_runner/cli.py`:

- Add `--context` to `build_parser()`: optional, not part of the existing `--task` /
  `--task-text` mutually-exclusive group (it is an independent, optional input per
  CONTRACT.md §2's `--context context.md` — a single file-based flag, no text-inline
  variant, matching CONTRACT.md §2's documented surface exactly)
- Add `_load_context(args) -> Optional[str]`, mirroring `_load_task`'s shape: `None`
  when `--context` is not given; otherwise reads the file and returns its content, or
  raises `ConfigError` with a message in the same style as `_load_task`'s
  (`f"cannot read context file '{args.context}': {exc}"`) on an `OSError`
- Wire the loaded value through to `run(..., context=<loaded value>)` in `main()`

### 2. Adapter-shape fixture assets

New fixtures under `tests/fixtures/adapter/` (or inline in the new test module if a
directory adds no value — Coding Agent's judgment, but keep the DoD/context/tools
content realistic and non-trivial, not one-line stubs):

- A DoD-shaped task text (e.g. a short "Definition of Done" checklist, the shape an
  epic spec's DoD section actually takes — bullet points with concrete pass/fail
  conditions, not a vague prose instruction)
- A scoped epic spec/starter excerpt for `--context` (a few paragraphs of Context/Goals-
  shaped text, the kind of scoped material §7 step 2 describes — never a full governance
  dump, consistent with §6's token-discipline invariant)
- A coding-set `tools.json`: `enabled` drawn from the §4 built-in coding set
  (`read_file`, `write_file`, `edit_file`, `list_dir`, `run_command`, `git` — or a
  realistic subset), with `allow_paths` scoped to a repo-shaped directory, matching
  CONTRACT.md §4's example shape

### 3. Adapter-pattern fixture tests

A new test module (e.g. `tests/test_adapter_contract.py`) exercising the CLI (`main()`,
scripted client — reuse or extend the message-recording `FakeClient` pattern already
established in `tests/test_loop.py`, which records `model`/`messages`/`tools`/`options`
per call, since this Epic needs to assert on message content, not just call count) with
the adapter-shape fixture assets from §2 as `--task`/`--context`/`--tools`, and an
explicit `--model` tag (do not rely on the CLI default — §7 step 2 says the shim always
passes an explicit tag):

- **Exit 0 (completed):** scripted final-answer response; assert exit code `0`, and
  assert the written `--transcript` JSON is valid and contains exactly the §3 Result
  keys (`status`, `final_answer`, `transcript`, `iterations`, `tokens`, `model`,
  `duration_ms`) with `status == "completed"` — do **not** assert anything about
  `final_answer`'s content (only its presence as a key, per SN-3)
- **`--context` reaches the model:** using the message-recording `FakeClient`, assert
  the first recorded call's `messages` contains a system-role message whose content
  equals the `--context` fixture file's content, appearing before the user-role task
  message — proving the CLI's `--context` value actually reached `run()` and was seeded
  correctly, not just accepted and discarded
- **Exit 2 (did-not-converge):** script `max_iterations` tool-call rounds with no
  `FinalAnswer` under the same adapter-shape inputs; assert exit code `2` and that the
  transcript is still valid, structurally-complete §3 JSON (`status ==
  "max_iterations_exceeded"`)
- **Exit 3 (config error):** an adapter-shape invocation with a broken input (e.g. an
  unreadable `--context` file, or a `tools.json` naming a tool absent from the coding
  set); assert exit code `3` and the single-line stderr convention already established
  by the rest of the CLI test suite (`local-agent-runner: `-prefixed, one line)
- **Exit 4 (runtime error):** an adapter-shape invocation with a scripted client failure
  (`OllamaClientError` or equivalent, matching the existing
  `test_connection_error_injected_client` pattern in `tests/test_cli.py`); assert exit
  code `4`
- Every exit-code test in this module uses the **same** adapter-shape task/context/tools
  fixtures (only the model script or one deliberately-broken input differs) — the point
  is proving one consistent invocation *pattern* is stable across all four outcomes, not
  four unrelated scenarios that happen to share a directory

### 4. `--context` unit coverage in `tests/test_cli.py`

Extend the existing CLI test suite (not the new adapter-pattern module) with the
smaller, mechanical `--context` cases that belong alongside `--task`'s existing
coverage:

- `--context` omitted: behavior is unchanged from before this Epic (no context message
  seeded) — a regression guard, not new behavior
- Unreadable `--context` file → exit `3`, mirroring `test_unreadable_task_file`'s
  existing shape and assertion style exactly

## Definition of Done

- [ ] `--context` reads a file and its content reaches `run()`'s `context` parameter
      unchanged; when omitted, behavior is identical to pre-Epic (no context message
      seeded)
- [ ] An unreadable `--context` file produces exit code `3` with a single
      `local-agent-runner: `-prefixed stderr line, matching the existing `--task`
      error-handling convention
- [ ] A fixture reproducing CONTRACT.md §7 step 2's exact invocation pattern (DoD-shaped
      `--task`, scoped `--context`, coding-set `--tools`, explicit `--model`) runs the
      CLI end-to-end offline (scripted client, no GPU/Ollama/network) and succeeds using
      only exit code `0` + the `--transcript` JSON's structural shape — the test never
      asserts on `final_answer`'s content
- [ ] The same adapter-shape fixture inputs, varied only by model script or one broken
      input, reach exit codes `2`, `3`, and `4` exactly as M2's CLI already guarantees
      generically — no regression, now proven under the shim's specific shape
- [ ] A dedicated test confirms `--context`'s file content is seeded as a system-role
      message ahead of the task message in the messages sent to the model
- [ ] `run(...)`'s public signature is unchanged (its `context` parameter already
      existed; this Epic only wires the CLI to it)
- [ ] All unit tests pass via `pytest`, fully offline
- [ ] Delivery Notice produced and committed
- [ ] All changes committed to `epic/E3.1` branch, delivered for merge to `milestone/M3`

## Execution Notes

- Build order: `--context` flag + `_load_context` in `cli.py` → the two mechanical unit
  cases in `tests/test_cli.py` → adapter-shape fixture assets → the four exit-code
  fixture tests in the new module, sharing one set of fixture inputs throughout.

  new adapter-contract test module (it needs to assert on message *content*, not just
  call count) — either import/reuse it or add an equivalent to the new module; do not
  reintroduce the simpler call-counting `FakeClient` from `tests/test_cli.py` for the
  message-order assertion, since that variant does not record message content.
- Keep the fixture assets realistic enough to be a meaningful stand-in for a real
  epic's DoD/context excerpt — the fixture's value is in reproducing the *shape* §7
  describes, not in being minimal.

## Notes

- Epic-level decisions settled in this spec (do not reopen without a spec amendment):
  - **`--context` is a single file-based flag, not a mutually-exclusive text/file
    pair.** CONTRACT.md §2 documents exactly `--context context.md`; there is no
    `--context-text` in the contract, unlike `--task`/`--task-text`. Adding one would be
    scope beyond what §7's invocation pattern or §2's documented surface calls for.
  - **The adapter-pattern fixture tests must never assert on `final_answer`'s content.**
    This is the direct enforcement of the binding SN-3 constraint carried from the
    Milestone spec — success in these tests is proven by exit code and transcript
    structure alone, exactly as a real adapter is required to consume the runner.
  - **One consistent fixture shape across all four exit codes**, not four unrelated
    fixtures. The Epic's purpose is proving the *pattern* is stable, which only a shared
    fixture with a single varied input (the model script, or one deliberately-broken
    field) can demonstrate.
