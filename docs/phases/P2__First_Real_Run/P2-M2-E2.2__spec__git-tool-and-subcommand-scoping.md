# Epic E2.2 — git Tool & Subcommand Permission Scoping

## Context

E2.1 (merged to `milestone/M2`) added `write_file`/`list_dir`, bringing every file tool
under identical `allow_paths` enforcement. A real Epic can now create and inspect files
but still cannot commit its work — the last built-in CONTRACT.md §4 lists,
`git(args)` scoped by `allow_subcommands`, doesn't exist yet.

This Epic adds `git` as a built-in tool, invoked **without a shell** (`subprocess.run(["git",
*tokens], shell=False, ...)`), gated by a new `allow_subcommands` permission knob that
name-matches only the first token of the parsed arguments. Denied subcommands, parse
failures, and timeouts all come back as deterministic, model-facing `ToolResult` errors —
`execute_tool` continues to never raise (§5's repair loop feeds these back to the model).

---

## Problem Statement

Without `git`, a real Epic's Coding Agent can edit and create files but cannot record
its work in version control — the one action every coding Epic needs to finish. An
unscoped `git` (or one that shells out with string interpolation) would also be able to
run arbitrary destructive or network-reaching subcommands (`push`, `clone`, `reset
--hard`); `allow_subcommands` is the guardrail, mirroring `run_command`'s
`allow_commands`/`deny_commands` pattern but scoped to git's own subcommand vocabulary.

---

## Goals

By the end of this Epic, the system must:

1. Provide `git(args)`: parses `args` into argv tokens and runs `git` as a real
   subprocess (`shell=False` — no string-interpolated shell, unlike `run_command`)
2. Add `allow_subcommands` to `ToolPermissions`: a list of exactly-matched git
   subcommand names (e.g. `["status", "add", "commit", "diff", "log"]`); **deny by
   default** (absent/empty list denies every subcommand), consistent with the deny-by-
   default rule the other permission knobs already follow
3. Enforce permission on the **first token** of the parsed `args` only — global flags
   before the subcommand are not supported; the model must pass the subcommand first
   (e.g. `"status --short"`, `"commit -m 'msg'"`, `"diff HEAD~1"`)
4. Return every expected failure (denied subcommand, no subcommand provided, unparsable
   `args`, timeout) as a deterministic error result; unexpected exceptions continue to
   be caught by the existing `execute_tool` wrapper — `_git` itself never needs a
   bare `except Exception`
5. Report `git`'s result in the same fixed, capped format `run_command` already uses
   (exit code, stdout, stderr via `_cap_stream`/`OUTPUT_CAP`); a non-zero exit code is a
   **successful** tool result — e.g. `git commit` with nothing staged, or `git diff
   --exit-code` with differences, is information for the model, not a tool failure
6. Cover all of it with offline unit tests against real local git repositories
   (`git init` in `tmp_path` — no network, no remote)

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Add a `deny_subcommands` knob — CONTRACT.md §4's table lists only
  `allow_subcommands` for `git`; unlike `run_command`, there is no paired deny list
- Add a working-directory/`cwd` permission knob — `git`, like `run_command`, runs in the
  process's current working directory; no new knob is introduced
- Support global flags or multiple subcommands ahead of the enforced token (e.g. `git -C
  /other/repo status`) — the first token of `args` is always the enforced subcommand
- Implement the SN-3 final-answer repair nudge (E2.3)
- Change `run_command`, `read_file`, `edit_file`, `write_file`, or `list_dir`
- Require network access in any test — `push`/`clone`/`fetch`/`pull` are exercised only
  as **denied-subcommand** cases (never actually invoked), keeping the suite fully
  offline

## Scope of Work

### 1. `ToolPermissions.allow_subcommands`

- New field `allow_subcommands: List[str] = field(default_factory=list)` on
  `ToolPermissions`
- `from_dict` reads `data.get("allow_subcommands") or []`, matching the existing
  pattern for `allow_commands`/`deny_commands`
- New method `subcommand_permitted(name: str) -> bool`: exact string membership in
  `allow_subcommands` (not `fnmatch` — git subcommands are discrete tokens, not glob
  patterns). Absent/empty list denies every subcommand (deny by default)

### 2. `git` tool definition

Wire-format definition (flat primitive schema): `args` (string, required) — the full
argument string to pass to `git`, **not including the leading `git` itself** (e.g.
`"status --short"`, `"add app.py"`, `"commit -m 'fix bug'"`). Description written for a
local model, stating the subcommand must come first and must be one the caller has
permitted.

### 3. `_git` handler

`_git(arguments, permissions) -> ToolResult`:

1. Require `args` as a string (reuse `_require_string`)
2. Parse `args` into tokens with `shlex.split` (POSIX mode). A `ValueError` (unbalanced
   quotes) is a deterministic parse-error result, not a crash
3. If parsing yields zero tokens, return a deterministic "no subcommand provided" error
4. The first token is the subcommand; check
   `permissions.subcommand_permitted(subcommand)`. Denied → deterministic error naming
   the denied subcommand and the permitted list (sorted), mirroring
   `_MSG_COMMAND_DENIED`'s phrasing style but for subcommands specifically
5. Execute `subprocess.run(["git", *tokens], shell=False, capture_output=True,
   text=True, timeout=permissions.timeout)` — reuses the existing `timeout` knob
   already on `ToolPermissions` (no new timeout knob for git)
6. `subprocess.TimeoutExpired` → deterministic timeout error (same shape as
   `run_command`'s, naming the full invoked command as `git {args}`)
7. On completion, format success output identically to `run_command`'s fixed block
   (`exit_code:` / `stdout:` / `stderr:`, each stream capped via `_cap_stream`); a
   non-zero `returncode` is `ok=True`

### 4. Tool registry

- Add `git` to `_DEFINITIONS` and `_HANDLERS`
- Update `_TOOL_ORDER` to `["read_file", "write_file", "edit_file", "list_dir",
  "run_command", "git"]` — appends `git` at the end, matching CONTRACT.md §4's table
  order in full

### 5. Unit tests

Extend `tests/test_tools.py` (offline; a real local `git init` repo per test via
`tmp_path`, `git config user.name`/`user.email` set locally so `commit` works with no
network and no global git config dependency):

- Allowed subcommand runs against a fixture repo (`status`, `add`, `commit`, `diff`,
  `log`) — exit code, stdout, stderr reported; commit actually recorded (verified via
  `git log`)
- Non-zero exit is a successful result: e.g. `git commit` with nothing to commit
  (non-zero exit, `ok=True`, message visible in output)
- Denied subcommand (e.g. `push`, `clone`, `reset`) → deterministic error; **the
  subprocess is never invoked** (assert via a repo/working-directory side effect that
  would only occur if git actually ran, or via monkeypatching `subprocess.run` to fail
  the test if called)
- No subcommand provided (empty/whitespace-only `args`) → deterministic error
- Unparsable `args` (unbalanced quote) → deterministic parse error, not an exception
  escaping the handler
- Timeout: monkeypatch `subprocess.run` to raise `subprocess.TimeoutExpired` (git has no
  reliable equivalent to `run_command`'s `sleep` fixture) → deterministic timeout error
- Deny-by-default: `ToolPermissions()` with no `allow_subcommands` denies every
  subcommand; `from_dict` parses `allow_subcommands` from the §4 dict shape
- `tool_definitions`/`execute_tool` integration: `git` appears when enabled and is
  dispatchable through `execute_tool` by name; `_TOOL_ORDER` includes `git` last

## Technical Constraints

**Language:** Python; changes confined to `local_agent_runner/tools.py`,
`tests/test_tools.py`
**Command execution:** `subprocess.run(["git", *shlex.split(args)], shell=False,
timeout=permissions.timeout)` — never `shell=True` for `git` (unlike `run_command`,
where `shell=True` was spec-settled in E1.3)
**Argument parsing:** `shlex.split` (POSIX mode); a `ValueError` is a deterministic
error, not a crash
**Testing:** pytest, fully offline; `tmp_path` fixtures with `git init` +
locally-scoped `user.name`/`user.email`; no network
**Environment:** must run inside a container (CONTRACT.md §10.3); no host-specific
paths; the container must have `git` on `PATH` (already true for the runner's own repo
operations)

## Notes

- Epic-level decisions settled in this spec (do not reopen without a spec amendment):
  - **`git` never uses `shell=True`.** `run_command`'s `shell=True` was a deliberate
    E1.3 trade-off for arbitrary shell commands; `git` doesn't need shell features, so
    it runs as a literal argv list — strictly safer, no shell-injection surface at all.
  - **No `deny_subcommands` knob** — CONTRACT.md §4's table gives `git` only
    `allow_subcommands`; adding a symmetrical deny list would be scope beyond the
    contract.
  - **Only the first parsed token is checked** — no support for global flags before the
    subcommand. A model that needs `-C <dir>` semantics isn't served by this Epic; it
    isn't required by the Milestone spec's goals either.
  - **`git` reuses the existing `timeout` knob** (already on `ToolPermissions` for
    `run_command`) rather than introducing a second timeout permission.
  - **Non-zero exit is a successful tool result** — consistent with `run_command`'s
    existing rule; a failed `commit` or a `diff --exit-code` hit is information for the
    model, not a tool failure.
