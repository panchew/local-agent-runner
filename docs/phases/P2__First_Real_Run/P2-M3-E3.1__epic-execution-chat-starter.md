### Summary

Add a `--context` CLI flag (file-based, optional) wired to `run()`'s existing `context`
parameter, then prove — offline, against a fixture reproducing CONTRACT.md §7 step 2's
exact invocation pattern (DoD-shaped task, scoped context, coding-set tools, explicit
model tag) — that all four exit codes and the `--transcript` §3 Result JSON are the
adapter's complete, stable, sufficient signal, without ever depending on `final_answer`.

### Problem Statement

`run()` has accepted a `context` parameter since P1, but the CLI never surfaced it — a
gap P1 explicitly deferred. Until it's closed and proven against the shim's exact
invocation shape, the adapter Epic on the ai-project-system side has nothing real to
integrate against: the flag doesn't exist, and no test targets the shim's specific
pattern (DoD task + scoped context + coding tools + explicit model) as a named scenario
proving the runner's contract-facing signals hold under it.

### Goals

1. Expose `--context` on the CLI: reads a file, passes its content unchanged to `run()`'s
   `context` parameter — mirrors `--task`'s existing file-loading shape
2. Reproduce CONTRACT.md §7 step 2's exact invocation pattern in an offline fixture
   (scripted client, no GPU/Ollama/network)
3. Prove exit code `0` + `--transcript` JSON structure — never `final_answer` content —
   fully determine success under that fixture (SN-3)
4. Prove exit codes `2`/`3`/`4` remain reachable and stable under the same fixture shape
5. Prove `--context`'s content is seeded as a system-role message ahead of the task
   message, via a message-recording scripted client
