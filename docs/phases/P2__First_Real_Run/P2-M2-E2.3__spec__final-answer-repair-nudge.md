# Epic E2.3 — Final-Answer Repair Nudge (SN-3)

## Context

E2.1 and E2.2 (merged to `milestone/M2`) completed the tool library CONTRACT.md §4
describes. This Epic touches a different part of the contract: §5's execution loop
(`local_agent_runner/loop.py`), landing the SN-3 steering-note requirement from the
v1.0.0 audit — the terminating turn (`final_answer`) is systematically unreliable on
Q&A-shaped tasks with `qwen2.5-coder:14b`, while tool calls, transcripts, and exit codes
are solid. This Epic adds a small, strictly bounded corrective step that improves
`final_answer`'s usability **without** making it, or the nudge itself, a new signal
anything downstream may depend on.

---

## Problem Statement

Two failure shapes were observed in the v1.0.0 audit:

1. **A junk terminating turn.** The model emits a leftover tool-call-shaped blob (e.g.
   `{"name": null, "arguments": {}}`, or empty content) instead of a real answer.
   `parse_tool_call` correctly classifies this as `FinalAnswer` (per its own contract:
   *unparseable-as-a-valid-call* content is an answer, not an error) — but the "answer"
   is useless to a human or log reader.
2. **Q&A ceiling exhaustion.** On a task that didn't need tools, the model keeps
   attempting (or repairing) tool calls until `max_iterations` is exhausted, and the run
   ends with no answer at all (`final_answer = None`, `status =
   max_iterations_exceeded`).

Neither is a §5 correctness bug — the loop already terminates deterministically in both
cases. The gap is usability: a human reading the transcript, or a log pipeline scanning
for a readable answer, gets nothing useful. The nudge closes that gap with **at most one**
additional, tools-disabled model call — never a second attempt, never a loop, and never
a change to `status` (the loop's own convergence signal is not touched by whether the
nudge happened to produce readable text).

---

## Goals

By the end of this Epic, the system must:

1. Detect a **junk terminating turn**: a `FinalAnswer` whose content is empty/whitespace,
   or parses (whole-content or via the existing ```json fence convention) as a JSON
   object containing a `"name"` key — the unmistakable shape of a failed tool-call
   attempt leaking through as if it were prose
2. Detect **ceiling exhaustion**: the loop's `max_iterations` tool-rounds are consumed
   without ever producing a `FinalAnswer`
3. On either trigger, issue **exactly one** additional `client.chat(...)` call with
   `tools=None` (no tool schema sent — the model cannot attempt a call) and a corrective
   user-role message asking directly for a plain-text answer; whatever content comes
   back becomes `final_answer`, **even if it is itself unusable** — there is no second
   nudge, no retry loop
4. Never change `status`: a junk-terminating-turn run stays `completed` (a `FinalAnswer`
   was already produced; the nudge only replaces its content); a ceiling-exhaustion run
   stays `max_iterations_exceeded` (the nudge only populates `final_answer`, which was
   `None` before — it does **not** promote the run to `completed`). §5's deterministic
   termination signal (`status`) is inviolable; only the human-facing text changes
5. Never raise and never add unbounded latency: if the corrective call itself fails
   (`OllamaClientError`), fall back to the pre-nudge result untouched — the nudge is a
   best-effort improvement, not a new failure mode
6. Account for the corrective call's cost: add its `eval_count` to `Result.tokens` and
   let it fall naturally inside `Result.duration_ms` (§6 token discipline — no silent,
   unaccounted model call)
7. Cover both trigger conditions with offline unit tests against recorded/mocked
   responses (scripted `FakeClient`, no GPU, no Ollama, no network)

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Make `final_answer` an adapter success signal — it remains explicitly unreliable-by-
  design from a consumer's point of view; `status` and the CLI exit code are the only
  contract-backed signals (per the binding SN-3 constraint)
- Add a second corrective attempt, a retry loop, or any mechanism that could make a run
  take more than one extra model call
- Increase `max_iterations`, add a new CLI flag, or otherwise change the loop's public
  `run(...)` signature
- Record the corrective round in `Result.transcript` — `transcript` is specifically
  "one step per tool round" (per `loop.py`'s existing docstring); the corrective call
  makes no tool call and is not a tool round
- Classify "Q&A-shaped" tasks semantically — the loop cannot know a task's shape ahead
  of time; the ceiling-exhaustion trigger fires on **any** run that exhausts
  `max_iterations` without a `FinalAnswer`, which is the only thing the loop can
  actually observe (documented as a deliberate simplification, not a gap)
- Touch `tools.py`, the tool library, or any permission model (E2.1/E2.2's concern)
- Touch the CLI (`cli.py`) or its exit-code mapping

## Scope of Work

### 1. Junk-terminating-turn detection

A module-level predicate in `local_agent_runner/loop.py`:

```
def _is_unusable_final_answer(content: str) -> bool
```

- Empty or whitespace-only content → unusable
- Otherwise, apply the same content-extraction convention already used elsewhere in
  this file (```json fence if present, else the stripped whole content) and attempt
  `json.loads`. If it parses to a `dict` containing the key `"name"` → unusable (this is
  the exact shape of a failed/partial tool-call attempt, e.g. `{"name": null,
  "arguments": {}}` or `{"name": "read_file"}` with no closing braces recovered) —
  reuse the existing `_JSON_FENCE` regex already defined in this module; do not add a
  second one
- Anything else (real prose, including prose that happens to contain braces but isn't a
  parseable `{"name": ...}` object) → usable, no nudge

### 2. The corrective call

A single helper, e.g. `_request_plain_answer(client, model, messages, options,
nudge_text) -> Optional[Tuple[str, Optional[int]]]`:

- Appends the corrective message (`{"role": "user", "content": nudge_text}`) to a
  **copy** of the running `messages` list (the original list must not be mutated if the
  caller needs to preserve it for other purposes — though in practice this is the last
  thing the loop does before returning)
- Calls `client.chat(model, messages, tools=None, options=options)` — `tools=None` is
  significant: passing `None` (not `[]`) matches how a plain Q&A call already looks to
  `OllamaClient.chat` (the `tools` key is omitted from the payload entirely, per its
  existing `if tools is not None:` guard) — this is not a new code path in the client,
  just calling it the way a tool-free chat already works
- Returns `(content, eval_count)` on success; on `OllamaClientError`, catches it and
  returns `None` — the caller falls back to the pre-nudge result

### 3. Two corrective texts (module-level string constants)

- One for the junk-terminating-turn case (e.g. "Your previous response was not a usable
  answer. Please reply now with a plain-text final answer to the task above — no tool
  calls, no JSON.")
- One for the ceiling-exhaustion case (e.g. "You have used all available tool calls
  without giving a final answer. Based on everything you have done so far, reply now
  with a plain-text final answer to the task above.")

### 4. Wiring into `run(...)`

- **Junk-terminating-turn branch:** where `run(...)` currently does `if
  isinstance(parsed, FinalAnswer): return result(STATUS_COMPLETED,
  final_answer=parsed.content)`, insert the check: if
  `_is_unusable_final_answer(parsed.content)`, attempt the corrective call (appending
  `response.message` to `messages` first, exactly as the tool-round branch already does,
  so the model's own prior turn is in context) using the junk-case nudge text. On
  success, add the corrective `eval_count` to `tokens` and return `result(
  STATUS_COMPLETED, final_answer=<corrective content>)` — **status stays `completed`
  either way**; on failure (or if the corrective call itself also raises), return
  `result(STATUS_COMPLETED, final_answer=parsed.content)` — the original junk content,
  unchanged, exactly as today
- **Ceiling-exhaustion branch:** where `run(...)` currently falls out of the `for` loop
  to `return result(STATUS_MAX_ITERATIONS_EXCEEDED)`, insert the same corrective-call
  attempt (append the *last* `response.message` from the loop to `messages` first) using
  the ceiling-case nudge text. On success, add the corrective `eval_count` to `tokens`
  and return `result(STATUS_MAX_ITERATIONS_EXCEEDED, final_answer=<corrective content>)`
  — **status stays `max_iterations_exceeded`**; on failure, return
  `result(STATUS_MAX_ITERATIONS_EXCEEDED)` exactly as today (`final_answer=None`)
- Neither branch touches `transcript` — `iterations` (`len(transcript)`) is unaffected
  by the nudge in both cases

### 5. Unit tests

Extend `tests/test_loop.py` (offline; scripted `FakeClient`, no GPU/Ollama/network):

- **Junk-terminating-turn trigger:** a fixture-style response whose content is
  `{"name": null, "arguments": {}}` (or an incomplete tool-call fragment), scripted as
  the first response, followed by a scripted plain-text corrective response — asserts
  `status == "completed"`, `final_answer` equals the corrective text (not the junk), the
  corrective call's `eval_count` is reflected in `Result.tokens`, and `transcript` is
  unchanged (no new step added — same length as if the junk answer had been accepted
  directly)
- **Empty/whitespace final answer also triggers the nudge:** content `""` or `"   "` is
  detected as unusable
- **A real prose final answer is never nudged:** confirm `FakeClient.calls` has length 1
  (no second `chat()` call) when the first response is ordinary prose, even prose
  containing literal `{` characters that don't parse as a `{"name": ...}` object
- **Ceiling-exhaustion trigger:** script `max_iterations` tool-call rounds (e.g. all
  `read_file`) so the loop exhausts its budget, then one more scripted response for the
  corrective call — asserts `status == "max_iterations_exceeded"` (unchanged), and
  `final_answer` is now populated with the corrective content (previously `None`)
- **Corrective call failure falls back cleanly, both branches:** monkeypatch/script the
  `FakeClient` to raise `OllamaConnectionError` on the corrective call only — for the
  junk-terminating-turn case, assert the run still returns `status == "completed"` with
  the **original junk content** as `final_answer` (not an exception, not `status ==
  "error"`); for the ceiling-exhaustion case, assert `status ==
  "max_iterations_exceeded"` with `final_answer is None`, exactly as pre-Epic behavior
- **Never more than one corrective call:** even when the corrective response is itself
  unusable-shaped (e.g. also `{"name": null}`), assert the loop does **not** attempt a
  second corrective call — `final_answer` is set to that second response's raw content
  as-is, and `FakeClient.calls` has exactly one more call than the pre-nudge scenario,
  never two more
- **`max_iterations` is never exceeded:** for the ceiling-exhaustion case, assert
  `len(FakeClient.calls) == max_iterations + 1` exactly (the scripted budget plus the
  one corrective call) — never `max_iterations + 2` or more
- **`transcript`/`iterations` unaffected:** in both trigger scenarios, `Result.iterations
  == len(Result.transcript)` continues to hold and its value is identical to what it
  would have been without the nudge firing

## Definition of Done

Epic E2.3 is complete when:

- [ ] A junk terminating turn (empty content, or a parsed `{"name": ...}`-shaped object)
      triggers exactly one corrective, tools-disabled call; `final_answer` is replaced
      with its content; `status` remains `completed`
- [ ] Ceiling exhaustion (no `FinalAnswer` within `max_iterations`) triggers exactly one
      corrective, tools-disabled call; `final_answer` (previously `None`) is populated
      with its content; `status` remains `max_iterations_exceeded`
- [ ] A real prose final answer never triggers the nudge (no extra `chat()` call)
- [ ] The nudge never fires more than once per run, in either trigger branch, even if
      its own response is itself unusable
- [ ] A corrective-call failure (`OllamaClientError`) falls back to the pre-nudge result
      exactly — no new exception path, no `status` change
- [ ] The corrective call's `eval_count` is included in `Result.tokens`; `transcript`
      and `iterations` are unaffected by the nudge in both branches
- [ ] `run(...)`'s public signature is unchanged
- [ ] All unit tests pass via `pytest`, fully offline
- [ ] Delivery Notice produced and committed
- [ ] All changes committed to `epic/E2.3` branch, delivered for merge to `milestone/M2`

## Notes

- Epic-level decisions settled in this spec (do not reopen without a spec amendment):
  - **`status` is never changed by the nudge.** A `completed` run stays `completed`; a
    `max_iterations_exceeded` run stays `max_iterations_exceeded`. Only `final_answer`'s
    content can change. This is the direct enforcement of the binding SN-3 constraint
    that `final_answer` must never become a de-facto adapter success signal — the exit
    code (§2, derived from `status`) is untouched by whether the nudge produced readable
    text.
  - **At most one corrective call, full stop.** Even if the corrective response is
    itself unusable-shaped, there is no second attempt — its raw content becomes
    `final_answer` regardless. This is what makes the bound provable: the loop makes at
    most one model call beyond what `max_iterations` already allows for, in exactly two
    well-defined places.
  - **Ceiling-exhaustion detection is purely mechanical** — "no `FinalAnswer` within
    `max_iterations`" — not a semantic judgment about whether a task was "really"
    Q&A-shaped. The loop has no way to know that ahead of time; a legitimately long
    coding task that exhausts its budget gets the same one nudge attempt, which is
    harmless (worst case, the corrective response restates what the model already did).
  - **The corrective round is not a transcript step.** `transcript`/`iterations` measure
    tool rounds only; a tools-disabled corrective call is not one. Token cost is still
    accounted for in `Result.tokens` — invisible-but-free would violate §6.
  - **A corrective-call failure is silent, not a new error.** The nudge is best-effort;
    if it fails, the pre-nudge result is returned exactly as it would have been without
    this Epic. This Epic must not introduce any new way for a run to end in `status ==
    "error"`.
